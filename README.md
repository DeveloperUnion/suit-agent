# suit-agent

オーダースーツの顧客カルテ。採寸・注文・顧客の情報を 1 枚にまとめ、
**次に誰へ声をかけるべきかを知らせる**ことを狙っている。

やることは 2 つに絞ってある。

- **声をかける頃合いを知らせる。**お渡し後フォローと記念日の通知を見て、
  担当者が普段の連絡手段で 1 対 1 に連絡する
- **まとめて声をかける相手を引けるようにする。**業種・居住地で顧客を絞り、
  何かあったときにその範囲へ順に連絡していける

連絡そのものはこのシステムの担当ではない。**送信機能を持たない**（後述）。

データは Supabase。画面は `lib/data/*` だけを見て、境界は RLS が持つ。
設計と手順は `docs/database.md` と `docs/database-design.md`。

## 動かす

```bash
npm install
npm run dev        # http://localhost:3000
npm run build
npm run lint
npm run typecheck
npm run eval       # アシスタントの回帰テスト。dev サーバとローカル DB が要る
```

`eval` は実 API を叩くので **CI には入れていない**。鍵と課金と非決定性を持ち込む
と 1 ヶ月で無効化され、無効化された門は門が無いより悪い。プロンプトかモデルを
触る前後で手で回し、**前回との差**を見るためのもの。単一のスコアは出さない
（集計が 0.94 でも「電話番号だけ 2 割捏造」を隠せる）。

`.env.local` に要るものは 2 段に分かれる。**Supabase の 2 つが無いと画面が
1 枚も出ない**（`lib/supabase/client.ts` がその場で例外を投げる）。
残りはサーバ側の機能ごとの鍵で、無くてもアプリは動き、その機能を使ったときに
エラーで止まる。

```
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_ANON_KEY=...

GEMINI_API_KEY=...          # 発注書・名刺の読み取りと、パーソナルの埋め込み
OPENAI_API_KEY=...          # AI アシスタントの会話
WORKER_DATABASE_URL=...     # 埋め込みの書き込み（worker_role。下記）
CRON_SECRET=...             # 埋め込みバックフィルの Cron を守る合言葉
```

`WORKER_DATABASE_URL` はローカルなら
`postgresql://worker_role:worker@127.0.0.1:54322/postgres`（パスワードは
`supabase/seed.sql` が入れる）。本番の作り方は `docs/database.md`。

前の 2 つは `supabase status -o env` の出力。ローカルの DB の立て方は `docs/database.md`。

PR を立てると CI（`.github/workflows/db.yml`）が、使い捨ての DB へ全 migration を
まっさらから流して pgTAP を回し、あわせて `lint` と `typecheck` を通す。
main へマージすると同じコミットが本番 DB へ反映される。詳しくは `docs/database.md` の CI 節。

## やらないこと

作らないと決めたものを先に書く。ここが曖昧なままだと、要らないものが増える。

### 全員へ同じものを一斉に送らない

新作の告知のような、全員に同じ内容を届ける仕事は担当しない。
セグメント配信もリッチメニューも作らない。
ここで扱うのは **1 対 1 で誰に声をかけるか** だけ。

### メッセージを送らない・下書きも作らない

記念日やお渡し後の連絡は、担当者が**いま使っている連絡手段で手で**送る。
このシステムがやるのは「今日この人に連絡したほうがいい」と知らせるところまで。

送信機能を持たせない以上、AI の文面下書き、メッセージ履歴、送信チャネルの記録も持たない。
半端に記録だけ残すと、実際の会話は担当者の手元にあるのに、システム側にも断片が溜まって
どちらが本当か分からなくなる。

### 勤務先ニュースの巡回をしない

法人番号で企業ニュースを拾って話のきっかけにする、という案は取りやめた。
そのために置いていた法人番号・上場区分・会社 URL、および重要顧客フラグも削除している。
業種はニュースではなく一覧の絞り込みに使うので残している。

### 通知はアプリの中だけ

外部へプッシュしない。アプリを開けば「本日のアプローチ」に出ている、という形にとどめる。

## アプローチ（通知）の仕様

「今日連絡すべき人」は、事前にレコードを作らず **画面を開くたびにその場で評価して導出する**
（`lib/data/approaches.ts`）。閾値を変えたら即座に結果へ反映されるべきだから。
保存するのは、その結果に人が下した判断だけ。

### トリガーは 2 つ

| トリガー | 発火条件 |
|---|---|
| お渡し後フォロー | 最後のお渡しから **半年** または **1 年** が経った（既定） |
| 記念日 | 誕生日・初回購入記念日・結婚記念日などが **7 日前**（既定）から近づいた |

**どちらも設定画面から変えられる。**声をかける間隔も、声をかける準備に要る日数も、
やってみないと適切な長さが分からないため（`/settings` の一番右「トリガー」タブ。
実体は `app_settings` の 1 行で、**変えられるのは管理者だけ**）。
節目は 1〜3 個・各 1〜60 ヶ月・昇順、記念日の予告は 0〜60 日（0 は当日のみ）。
記念日は画面ではカウントダウン（「あと3日」）で見せる。

起点は **最後のお渡し** で、注文ごとには立てない。新しくお渡しがあれば、
古いお渡しのフォローはもう意味を持たないから。

**お渡し日が空の注文は納品日で代用する。**お渡し日は顧客の都合で決まるので発注書には
書かれておらず、空を理由にフォローが一生立たないほうが害が大きい
（`v_customers` の `coalesce(delivered_at, arrived_at)`）。
半年を逃したまま 1 年が来た場合は **1 年のほうだけ**を出す。そのとき言うべきことは
「1 年経ちました」であって「半年経ちました」ではない。

### 消えるのは押されたときだけ

通知は時間では消えない。**「連絡した」か「スキップ」を押すまで残る。**
見落としが勝手に消えてしまうと、気づかせるという目的を果たせない。

- **連絡した** — 対応済みとして履歴に残し、最終接触日を今日にする
- **スキップ** — 履歴には残すが、最終接触日は動かさない（連絡していないため）

判断は顧客単位ではなく **トリガー実体ごと**（`ApproachTask.triggerKey`）に保存する。

```
post_delivery:{orderId}:{節目の月数}m     6m / 12m / …
anniversary:{anniversaryId}:{発火する年}
```

顧客単位で持つと「お渡し半年後をスキップしたら 1 年後も出なくなる」「今年の誕生日を見送ったら
来年も出なくなる」ことになる。上の粒度なら、スキップした節目だけが閉じる。

鍵に埋めるのは節目の**月数**であって順番ではない。設定で 6 を 9 に変えれば鍵も `9m` に
変わり、半年で連絡済みの相手にも 9 ヶ月の通知が新しく立つ — 節目を変えたら出し直す、
という挙動になる。順番（1 つめ・2 つめ）を鍵にすると、月数を変えたのに「対応済み」と
判定されて**無音で出なくなる**。

### 表示は顧客ごとに 1 件

同じ人にお渡し後フォローと記念日が同時に立ったら、1 件へまとめて理由を 2 行並べる。
「連絡した」「スキップ」を押すと、立っているものはまとめて畳まれる。1 回の連絡で
どちらの話にも触れられるため。

**1 日に出す件数の上限は設けていない。** トリガーが 2 つだけならリストが溢れることはなく、
上限で隠すと「見えていない分がある」という不安のほうが残る。

## 画面

| パス | 内容 |
|---|---|
| `/dashboard` | 今月の目標・達成率、売上の月次推移、本日のアプローチ |
| `/customers` | 顧客一覧。氏名/カナ/会社名の検索、居住地・業種での絞り込み |
| `/customers/[id]` | 顧客カルテ。基本情報 / パーソナル / メモ / 採寸 / 注文履歴 / アプローチ |
| `/approaches` | 本日のアプローチ |
| `/settings` | 売上目標・スタッフ・トリガー（この並び。トリガーは滅多に触らないので右端） |

### カルテの箱の分け方

情報の置き場は「機械が値そのものを使うか」「その属性の人を全員引きたいか」の
2 つで決めている。

| | 置き場 | 例 |
|---|---|---|
| 機械が使う | 列 | 生年月日（記念日トリガー）、ネーム刺繍（発注書へ転記）、居住地・業種（一覧の絞り込み） |
| 全員引きたい | **パーソナル**（チップ） | ゴルフ、ネイビー、式典、出張多い |
| どちらでもない | **メモ**（1 行ずつ追記） | 「高橋様のご紹介」「ご子息の成人式スーツの相談（2027年予定）」 |

**下 2 つは同じテーブルで、ラベルが付いているかどうかしか違わない。**分けて持つと
「これは趣味欄か、メモか」を毎回選ばせることになり、速いほう（自由記述）へ
情報が逃げて検索から漏れる。入力は「1 行書く」に一本化してある。

**NG 事項だけは「注意事項」に隔離**して、カルテの一番上に出す。
パーソナルが類似検索で「引っ張り出す」ものなのに対し、こちらは開いた瞬間に
無条件で全件目に入るべきもの。取りこぼしが許される情報と許されない情報を、
同じ機構に載せない。

（写真掲載・夜間連絡の同意フラグも同じ枠に置いていたが、運用で一度も使われず
注意事項の視線を奪っていたので Phase 3 で列ごと落とした。）

採寸は、カルテ右上のシルエットから全画面の採寸ビューへ入る。
AI アシスタントは画面ではなく、どの画面にも出る右下の FAB から開く。

顧客はスタッフごとに分割していて、ログインした人には自分の顧客しか見えない。
絞り込みは `lib/data/customers.ts` の層で必ず効かせ、画面側の実装漏れで
他人の顧客が出ないようにしている。

## AI アシスタント

右下の FAB からどの画面でも開ける。スマホは全画面、`lg` 以上は右の側パネル
（`lg` では暗幕を出さず、背後のカルテを見ながら話せる状態にしている）。

**接客直後にスマホを片手で持ったまま、聞いた話をその場でカルテに残すための入口**。
両手でフォームを開いて入力する前提だと、聞いた話は結局残らない。
音声入力はボタンを押している間だけ聞き、離すと入力欄に入る（`lib/hooks/use-speech-recognition.ts`）。
**認識しても送信はしない。** 聞き違いを手で直せる状態で必ず一度止める。

### できること

顧客について**知ることは全部**、**残すことは提案として**扱える
（`app/api/agent/route.ts`）。

| 話しかけ方 | 動き |
|---|---|
| 「ゴルフが趣味な人だれだっけ」 | 語で顧客を引く（**上限なしで全件**）。件数を言い切る |
| 「アウトドア系が好きな人いたっけ」 | 語彙にある語へ展開して引き、加えて「近い人」を別枠で出す |
| 「時枝さんってどんな人だっけ」 | 検索せず、その人の記録を丸ごと読んで答える |
| 「時枝さんゴルフが趣味らしい」 | パーソナルへの追記を**提案** |
| 「光沢のある生地は苦手だって」 | 注意事項への追記を**提案** |
| 「電話番号が変わったって」 | 顧客の項目の更新を**提案**（現在値との差分を出す） |
| 「結婚記念日が 6 月 3 日らしい」 | 記念日の追加を**提案** |
| 「あの情報もう違うって」 | 記録の無効化を**提案**（行は消えない） |
| 「時枝さんには連絡しといた」 | 本日のアプローチを畳む**提案** |

### いま何をしているかを出す

道具を 2〜3 本回すと数秒かかる。**無音の 4 秒はスマホでは「固まった」に見える**ので、
道具を呼んだ時点で「お名前を照合しています」「カルテを読んでいます」を流している
（`lib/ai/tool-labels.ts`）。流す価値があるのは返答の文字より先にこちらのほう。

途中経過は画面の state に置くだけで **DB には書かない**。確定した 1 件だけを
`agent_messages` に入れるので、二重描画も競合も起きない。
道具を呼ぶ前は言えることが無いので「考えています」に倒す。

拾えなかった言い回しは、**できるふりをせずそう言って返す**。
「電話しといて」のような指示や、「今度ゴルフ誘うか」のようなこちらの意図は
**記録しない**。この線引きは `lib/ai/eval/cases.json` の約 1/3 を占める
「何も提案しないのが正解」のケースで守っている（`npm run eval`）。

### 検索は「全員」と「近いもの」を分ける

`app.search_customers()` 1 本が確定検索と意味検索を両方走らせる。
ツールを 2 本に分けて「網羅が要るときはこちら」と指示する形は採らない
（作法は必ず破れる）。

- **確定検索**はラベル・別名・本文の一致を**上限なしで全件**返す。
  「ゴルフが趣味の方は 12 名です」と言い切れることがこの検索の存在理由
- **意味検索**は「近いもの」として別枠。ラベルの付いていない走り書き
  （「休みの日は山に登ってるらしい」）を拾うのがこちらの担当
- 件数は一覧と**別のフィールド**で返す。モデルが散文にする過程で列挙を
  省いても、数字だけは削れない形にしてある

### 書き込む前に必ず見せる

パーソナルの追記は提案として出し、人が「適用」を押してから書き込む
（`components/agent/agent-action-card.tsx`）。名刺・発注書の読み取りと同じ方針で、
AI が出したものを黙って保存しない。趣味は接客の材料として使うものなので、
聞き違いがそのまま残ると次の接客で外す。

### 境界とデータ

- ツールは **RPC しか呼ばない**（`lib/ai/agent-tools.ts`）。`lib/ai/` から
  `lib/data/*` は import できない（ESLint）。あちらは画面のための関数で、
  上限や並び順が入っているので、使うと網羅性の担保を迂回した経路が静かに生まれる。
  顧客の絞り込みは `app.search_customers()` の中と RLS が担う。
  **会話から来た指示だからといって、その境界を越えさせない**
- **検索の既定は「RLS が許す全部」ではなく「自分の担当」。**管理者は全顧客を
  閲覧できるので、絞らないと管理者のときだけ画面と答えが食い違う
  （AI は 4 名と言うのに一覧は 3 名）。dev-seed で実際に踏んだ
- 会話は Provider の state ではなく `agent_messages` に残す（`lib/data/agent-chat.ts`）。
  接客の合間に開き直したり端末を持ち替えたりする使い方で、リロードのたびに消えると
  「さっき何を頼んだか」が追えなくなるため。分割は RLS が担う
- パーソナルは `customer_facts` に **1 事実 1 行**で持つ。ラベル（`fact_labels`）が
  付いていればカルテのチップに、付いていなければ「メモ」の走り書きとして出る。
  **メモと事実はラベルの有無しか違わない**ので、器を分けていない
- 語で引くときは**ラベルと本文の両方**を見る。走り書きに「ゴルフ」と書かれた顧客を
  落とさないため。上限は付けない — 該当 12 名のうち 5 名しか返さないと、
  落ちた 7 名は誰にも見えない

### いま見ている顧客を文脈にする

パネルは `app/layout.tsx` 直下に 1 つあるだけで、画面からは props が届かない。
`usePathname` を正規表現で解析するとルートが増えるたびに壊れるうえ顧客名も取れないので、
**画面側から名乗ってもらう**形にしている（`useAgentContext`、`customer-detail-view.tsx:58`）。
アンマウントで自動的に外れる。カルテを開いていれば、文中に名前が無くてもその人が相手になる。

### 右下の取り合い

FAB が右下を使うので、同じ場所を使っていたものを退かしてある。

- トーストは `app/layout.tsx` の `offset={{ bottom: "5.5rem" }}` で上へ
- Next.js の dev インジケータは `next.config.ts` の `devIndicators: false` で消した
  （z-index が極端に高く、重ね順では避けられないため）

FAB にツールチップは付けていない。タッチでは最初の 1 回がツールチップの表示に吸われ、
主戦場のスマホで入口が二度押しになる。

## 色の決め事

定義は `app/globals.css` の 1 ファイルに集約されている。TSX 側に色のハードコードは無い。

素材の比喩でトークンを持っている（テーラーの製図台から）。

| トークン | 役割 |
|---|---|
| `paper` | 製図紙。紫みを含んだ白 |
| `ink` | バイオレットブラック。本文と数値 |
| `brand` `#331e6d` | **読ませるもの** — 見出し・リンク・タグの文字・帳票の罫線 |
| `brand-fill` `#5b47a8` | **塗る面** — チャート・バー・選択中のチップ |
| `rule` | 細罫。紙の帳票の区切り線 |
| `measure` | メジャーの目盛りグレー。ラベル・補助情報 |
| `chalk` | 青チャコ。減少方向・情報 |
| `thread` | しつけ糸。警告・増加方向 — 唯一の暖色 |

`brand` と `brand-fill` を分けているのは、サイドバーの面（`#211a35`）と
濃い紫のコントラストが 1.22:1 しかなく、濃い紫でベタを塗ると画面の左右に
同じ濃さの紫が並んで潰れるため。塗りだけ 1 段明るい紫に逃がしてある（2.3:1）。

`chalk`（寒色＝減少）と `thread`（暖色＝増加・警告）は意味を担う色なので、
ブランドの色相を変えても触らない。

## データの持ち方で決めたこと

- **採寸データは紙の採寸票に準拠**する。要件定義書の ER 図と食い違う場合は
  `private/採寸データ.jpg` が正（`docs/README.md` 参照）。要件定義書は身体寸法と
  仕上がり寸法を別テーブルに分けていたが、実物は「実寸 / 上がり寸」が同じ行に
  並記されている。その変換こそが職人の判断なので、ペアで持つ
- **居住地は都道府県だけ**を住所と別に持つ（`residencePrefecture`）。
  自由記述の住所からは絞り込めず、災害時にその地域の顧客をまとめて拾えないため。
  選択肢は `lib/constants/prefectures.ts`
- **業種は定数から選ぶ**（`lib/constants/industries.ts`、46 件）。表記が揺れると
  同じ業界の顧客がまとまらない。ただし選択肢に無い勤務先は必ず出るので、
  「その他（自由記述）」で手入力も残してある。型が `Industry` ではなく
  `string` なのはそのため
- **顧客ランク（A/B/C）も重要顧客フラグも持たない**。手で付ける序列は形骸化するうえ、
  接客中に見せる画面に顧客の格付けを出すことになる
- **注文明細に仕様（胸ポケット・ベント・袖釦）を持たない**。あれは工場に伝えるためのもので、
  店側が後から見返す場面がない。扱うのは「何が売れていくらだったか」まで
- **生地マスタを持たない**。原反NO・色番・色名・組成はすべて発注書の上にあるので、
  マスタを引かず注文明細に文字列でそのまま持つ。マスタを別に育てる手間に見合う使い道が
  無かった。代わりに「ネイビー無地はすでに2着」のような色系統の重複警告と保有色柄の内訳は
  出せなくなっている（正規化された系統がどこにも無くなったため）。
  保有アイテム種別と未保有は生地と無関係なので残っている
- **金額は「売上金額（税込）」の 1 欄だけ**。当初は工場発注書の右上と同じ 4 欄
  （売上金額・割増金額・消費税・合計金額）を並べていたが、紙のその欄は実運用では
  空欄のまま流れていて、店が持っているのは税込の 1 本だけだった。読み取りでも扱わず、
  取り込んだあと注文カードから入れる。割増を分けて持つかは審議中（`docs/todo.md`）。
  アイテム別の標準価格マスタは持たない。初期値を置いても人が上書きするだけだった
- **日付は受注日・納品日（工場→店）・お渡し日（店→客）の 3 つ**。顧客に約束する
  「納期」は持たない — 紙にその欄が無く、店が管理していたのは工場からいつ届くかのほうだった
- **連絡先は電話・メール・住所だけ**。送信を担当しない以上、外部サービスの ID を
  持っても埋める経路が無く、打つ手間と「連携済み」という誤解だけが残る
- 一覧の並びは**お渡しからの経過日数の降順**。列としては表示していないが、
  放置が長い顧客が上に来る順序は保っている

## 画面に文章を置くかどうか

図から読めることは書かない。ダッシュボードに「月の進みを上回っています」のような
判断の文は置いていない。数字とバーを見れば分かることを言い直す行が、
毎週見る画面では読み飛ばす行として溜まっていくため。

一方で、図では言えないこと（破線が何か、いちばん右のバーがまだ途中であること）は
注記として残す。

## AI の扱い

- `agent.ts` / `agent-loop.ts` / `agent-tools.ts` — 会話。**`gpt-5.6-luna` を呼ぶ**
- `extract-business-card.ts` / `extract-order-sheet.ts` — 名刺・発注書の読み取り。
  **Gemini（`gemini-3.6-flash`）を呼ぶ**
- `embed.ts` — パーソナルの埋め込み（`gemini-embedding-001`）

サーバ側（`app/api/*`）は API キーを隠すためだけに在る。**その裏返しとして、
認証を付け忘れたエンドポイントは API キーを世界中に配る口になる**ので、
入口は `lib/api/auth.ts` の `requireStaff` 1 本に寄せてある。
DB は利用者のトークンをそのまま載せて触るので、サーバを通したことで
見える範囲は広がらない（RLS が天井のまま）。

読み取りの PDF はネイティブに読めるので変換しない（画像に落とすと手書きの細部が消える）。

### 書き込む経路は 1 本しかない

AI が返せるのは `AgentAction` だけで、実際に書くのは
`lib/data/agent-apply.ts` の適用ハンドラ。**ここが実装していない種類の
書き込みは原理的に起こせない。**採寸値に触れるには型に `kind` を足し、
ハンドラを書き、カードにボタンを出す、という明確な行為が要る。

`lib/ai/` からは `lib/data/*` を import できない（ESLint）。読み取りが
`app.search_customers()` を迂回する経路を作らせないため。

読み取り結果はどの項目にも確信度を付けて返す。モデル自身に「その値をどれだけ確実に読めたか」を
申告させ、`CONFIDENCE_WARN`（0.7）を下回った項目だけ確認画面で「要確認」を出す。
全項目が同じ見た目で並ぶと結局すべて読み直すことになり、読み取りの意味がなくなる。

メッセージの下書き生成は持たない（「やらないこと」を参照）。
