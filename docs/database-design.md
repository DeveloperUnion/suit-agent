# データベース設計の判断

手順とファイルの役割は `docs/database.md`。ここは**なぜそうしたか**だけを書く。

前提: 顧客 約3,000件・スタッフ10名（管理者3名）。**極めて小規模**。
この規模であることを制約ではなく武器として使っている箇所が複数ある。

---

## 決めごとの一覧

| 項目 | 決定 |
|---|---|
| スタック | Vercel + Supabase。データアクセスは **supabase-js 一本** |
| 権限 | 管理者は**全顧客を閲覧のみ**。**編集は全員が自担当のみ**。書き込み側に例外を作らない |
| 認証 | 必須。招待制（Magic Link）。**門番は GoTrue の設定ではなく `auth.users` のトリガー** |
| アクセス制御 | **RLS に寄せる**。`lib/data/*` の自前 staffId 絞り込みは廃止 |
| AI の書き込み | **提案 → 人が「適用」を押してから書き込む**。閲覧ログは取らない |
| 検索 | **確定検索（全件）と RAG（近いもの）を 1 本の関数で両方走らせる** |
| バックアップ | PITR は入れない（+$100/月）。**「消えない」ことを設計で保証する** |
| 画像 | **1 枚も保存しない。**名刺も発注書も読んだら捨てる。着装写真は入れてから撤回した |

## 1. 事故は「作法」ではなく「構造」で防ぐ

| 守りたいこと | 作法（不採用） | 構造（採用） |
|---|---|---|
| 他人の顧客が見えない | 各関数で `.filter()` | RLS ポリシー |
| 監査ログの記録漏れ | 書き込み側で log を呼ぶ | 共通トリガー |
| AI が網羅すべき問いで取りこぼさない | 「網羅が要るときは確定検索を使え」と指示 | **ツールを 1 本にして中で両方走らせる** |
| 同じ語が人によって違う分類になる | 命名規約 | **`fact_labels` でカテゴリをラベルの属性にする** |
| RLS 付け忘れ / `security_invoker` 忘れ | レビュー | CI で機械的に検出 |

実例。`lib/data/customers.ts` の `updateCustomer` には `staffId` のチェックが
**無かった**。`listCustomers`/`getCustomer` は絞り込んでいるのに、id さえ分かれば
他人の顧客を書き換えられる。悪意ではなく単なる書き忘れで、**RLS ならこの関数を
1 行も変えずに塞げる**。

## 2. 小規模であることを武器にする

**検索基盤を作らない判断そのものを成果物として残す。**

- 顧客名検索は `search_key ILIKE` の seq scan（1〜3ms）。GIN/trgm も pg_bigm も
  PGroonga も入れない（managed で入らないことが多く、2ms のために移植性を捨てない）
- pgvector の HNSW も当面作らない。自担当で検索すると **RLS が 6,000 行に絞る**ので
  12MB の全走査で数十ms
- 追加基準だけ明文化: **chunk 5万行超、または p95 が 300ms 超**で HNSW

## 3. AI が「静かに間違える」経路を塞ぐ

怖いのはエラーではなく無音の誤り。

- **`field_key` に FK を張る** — jsonb だと存在しないキーは静かに NULL を返し、
  「記録がありません」と答えてしまう。実際はキー名の幻覚だった、が検出不能
- **網羅性が要る問いに RAG を使わない** — top-k は該当12名のうち7名を静かに落とす。
  「ゴルフ好きなのに案内が来なかった人」は誰にも見えない
- **カテゴリで検索を絞らない** — 分類が 1 回ずれただけで、その顧客が永久に引けなくなる

## RLS を選んだ最大の実利は「API 層が要らない」こと

モック期の `lib/data/*` は「将来 DB を入れるときは中身を差し替えれば済む」形にしてあった。
**RLS があるのでその約束がそのまま守れた** — 実測は `docs/database.md` の
「『画面は変わらない』はどこまで成り立ったか」（保存先の入れ替えそのものを理由とする
画面の変更は 0 行）。

supabase-js はブラウザから直接呼んでよく（境界は DB が持つ）、`lib/data/*` は
クライアントのまま中身が入れ替わった。RLS を採らなければ全クエリにサーバ層が
必要になり、この抽象が意味を失っていた。

サーバ側に置くのは API キーを隠す用途だけ。いまあるのは `app/api/extract/*`（Gemini）の
1 つで、Phase 2 で `app/api/agent/*`（会話）と `app/api/cron/embed`（埋め込み）が
増える（`docs/todo.md`）。

### 招待の門番を GoTrue から DB へ移した

`service_role` を置かないと決めた副作用として、**スタッフを増やす経路が
存在しなかった。**`auth.admin.inviteUserByEmail()` にはそのキーが要るので、
設定画面の `createStaff()` は `staff` に 1 行入れるだけで、その人は
サインインできない。本番の管理者は店舗の人なので、Supabase の Dashboard を
開かせる運用は成立しない。

**`enable_signup` を有効にして、代わりに `auth.users` へトリガーを 2 本置いた。**

| | 移行前 | 移行後 |
|---|---|---|
| 門番 | GoTrue の設定フラグ | `app.guard_auth_user_is_staff()` |
| どこにあるか | ダッシュボード | **git の中。pgTAP で検査できる** |
| 誰かがフラグを戻したら | 誰でもアカウントを作れる | **変わらず作れない** |
| スタッフを増やす | できない | 設定画面で名前とメールを入れるだけ |

**メール一致で `auth_user_id` を紐付けている。**`staff.auth_user_id` の当初の
コメントは「一致で紐付けない — 検証しない IdP を後から足したときになりすまし
登録が通る」と書いていて、その懸念は正しい。いまは入り口が Magic Link だけで、
**アドレスの所有はメールが届くことで証明される**ので成立している。
Google ログインのような別の IdP を足すなら、ここを見直すこと。

### `service_role` キーが唯一の穴

`BYPASSRLS` 相当で、Vercel の環境変数に置いた瞬間に天井が消える。
**置かない。**越境が要る用途（埋め込みバックフィル）は `BYPASSRLS` を持たない
`worker_role` を使う。「越境できる鍵が環境変数に存在しない」状態を作る。

### GRANT による二枚目の壁は無い

supabase-js（PostgREST）経由だと接続ロールは全員 `authenticated` 固定で、
人間と AI を Postgres が区別できない。**結果 RLS が唯一の砦**になり、
権限マトリクスのテストの重みが上がる。

ただし「提案 → 適用」を採ったことで、GRANT より強い保証が別途手に入っている（後述）。

## 管理者の「スタッフ切り替え」は なりきり ではなく 閲覧フィルタ

モックの `switchStaff()` は `session.staffId` を差し替える。この値は 2 つの意味を
持っている（`lib/auth/current-staff.ts` のコメント）:

- 誰の顧客を表示するか
- 採寸票・注文に「誰がやったか」として記録される操作者

**本番でこのまま実装してはいけない。**管理者が白髭さんに切り替えた状態で操作すると
「白髭さんがやったこと」になり、監査ログも嘘になる。分離する:

| | 本番での意味 |
|---|---|
| `app.current_staff_id()` | **常に本人**。RLS の主体であり監査の主体。切り替えても動かない |
| 「表示中のスタッフ」 | **UI の状態にすぎない。**クエリに `where staff_id = X` を足すだけ |

分離の利点は**新しい機構が 1 つも要らない**こと。SELECT は `or app.is_admin()` で
全部見えるので UI が絞り、UPDATE は `staff_id = app.current_staff_id()` なので
**他人のページを開いていれば自動的に編集不可**になる。

**AI の検索範囲もこれで決まる。**「RLS が天井、ツール引数が既定」の引数の正体は
「表示中のスタッフ」そのもの。画面で見えているものと AI が答えるものが常に一致する。

**代理接客の懸念は取り下げた。**出張採寸のため担当が変わらない（店舗確認済み）。

## AI の書き込みは「提案 → 適用」

`lib/types/index.ts` の `AgentMessage.applied_at` が機構の本体。

決め手は**後戻りの非対称性**。この機構があれば「趣味だけ自動適用」は `applied_at` を
即座に入れるだけで実現できるが、逆（即時 + revert から提案 → 適用へ）は作り直しになる。

### 波及: 人間と AI の書き分けが一切要らなくなった

承認が必ず挟まる以上、**できた行はすべて人間が作った行**。ゆえに:

- `customer_facts` に `created_by_actor_type` も `source='agent_chat'` も持たない
- `agent_actions` / `revert_agent_action()` の事後取り消し機構が丸ごと不要
- `change_log` の actor も常に人間

`source` が区別するのは `'manual' | 'agent' | 'migration'` の 3 つ。人が画面で書いたか、
会話から提案されたものを人が適用したか、機械が移したか。`'migration'` は既存の
`hobbies` 文字列を機械的に割る初期投入分で、**1 件ずつ承認していない唯一の経路**。
`"ゴルフ（月2回）"` が `label='ゴルフ（月2回）'` になる、といった誤りが一括で混ざり、
**混ざったことに誰も気づかない**。後から「これは移行時に機械が入れた行だ」と
言えることに意味がある。

### 波及: 「AI が採寸値を書く事故」も塞がる

AI が返せるのは `AgentAction` だけで、実際に書き込むのは適用ハンドラ。
**適用ハンドラが実装していない種類の書き込みは原理的に起こせない。**
採寸値に触れるには `kind` を型に足し、ハンドラを書き、UI にボタンを出す、という
明確な行為が要る。GRANT は「テーブル単位で拒否」だが、こちらは
**そもそも書き込む経路が存在しない**。

その分 lint の役割は読み取り側に縮む（`lib/ai/` で `supabase.from(` を禁止し
`supabase.rpc(` だけを許す）。

## パーソナル（Phase 2）— 「趣味に入れるべきだとどう判断するか」

LLM に分類させれば「それらしい答え」は毎回返るが、境界例（「ゴルフ場の設計をやってる」
「奥さんがゴルフ好き」「接待でゴルフばかり」）で**日によって違う答えを返す**。
そして人はそれを検証しない。問うべきは精度ではなく「**間違えたとき何が壊れるか**」。

### カテゴリを検索の絞り込みに使わない

`where category = 'hobby'` で絞ると、「ゴルフ場の設計」を `work` に分類された顧客は
「ゴルフが趣味な人」で**永久に引けない**。

**`label = 'ゴルフ'` だけで引く。**趣味だろうが仕事だろうが、接客上はすべて
「ゴルフの話ができる人」で、むしろ全部出たほうが役に立つ。`body` に原文が残るので
スタッフは一目で区別できる。カテゴリは表示の見出しにしか使わない。

### カテゴリはラベルの属性にする（`fact_labels`）

「ゴルフ」は誰にとってもゴルフ。発話のたびに分類させるから揺れる。
初出時に 1 回決めれば、2 回目以降は判断が発生しない。
分類を直したければ `fact_labels` を 1 行 UPDATE すれば全顧客に一斉反映される。

**一覧をプロンプトに載せられる**のが最大の実利。「打ちっぱなし行くらしい」→
一覧に「ゴルフ」がある → LLM が既存語に寄せる。embedding の類似度より確実で、
**この一覧を作れるのは正規化したからこそ**（文字列 1 本では不可能）。

### 結果、LLM が判断すべきことは 1 つだけになる

| 発話 | 判断 |
|---|---|
| 「国枝さんゴルフ好きらしい」 | **事実 → 記録する** |
| 「国枝さんに電話しといて」 | 指示 → 記録しない |
| 「国枝さんって誰だっけ」 | 質問 → 記録しない |
| 「国枝さん、今度ゴルフ誘ってみるか」 | こちらの意図 → 記録しない |

間違えても提案カードに出るので人が気づける。

### メモと事実は、ラベルが付いているかどうかしか違わない

当初は `memo` を列のまま残す予定だった（「facts に流すと一覧がノイズで埋まる」）。
**取り下げた。**

分けて持つと、スタッフに「これは趣味欄か、メモか」を**毎回選ばせる**ことになる。
その判断は接客の合間には重すぎるので、速いほう（textarea）へ情報が逃げる。
逃げた「ゴルフ好き」は確定検索に出てこず、RAG では出たり出なかったりする。
現れ方は例によって「ゴルフ好きなのに案内が来なかった人が 7 名いる」で、誰も気づけない。

**`customer_facts.label_id` を nullable にして 1 つにまとめた。**

- 入力は「1 行書く」だけ。ラベルは後から付く（会話経由か、カルテの「＋」）
- 心配していたノイズは起きない。汚れるのを恐れていたのは `fact_labels`（語彙の一覧）で、
  `label_id` が null の行はそこに **1 語も足さない**
- チャンクは常に 1 行 1 個。メモを 1 顧客 1 テキストのまま埋め込むより
  **RAG の精度が上がる**（「ワインが好きな人」でスコアが薄まらないのと同じ理屈）
- 上書きで消えない。走り書きにも訂正・無効化の履歴が付く

そのうえで、**確定検索はラベル一致と本文の全文一致の両方を LIMIT なしで返す**。
どちらに書いても取りこぼさないので、この選択は安全側に倒れている。
入力の摩擦（「メモに『ゴルフ』とあります、チップに足しますか」の提案）は入れない —
結局そこで箱を選ばせており、摩擦を後ろへずらしただけになる。

### 列の振り分け（判断基準は「ラベルで引く場面があるか」）

| | 行き先 | ラベルで引くか |
|---|---|---|
| `hobbies` / `preferences.*` | **facts**（ラベルあり） | 「ゴルフが趣味な人」「紺が好きな人」→ **ある** |
| `memo` | **facts**（ラベル無し） | **ない**。だからラベルを付けない。器は同じ |
| `familyInfo` | **列のまま** | 「長男がいる人」→ **ない**。接客直前に一文で読むもの |
| `tags` | **三分割**（事実→facts / 同意→列 / 「紹介元」→破棄） | 中身が 3 種類混在。「紹介元」は意味を持っていなかった |
| `ngNotes` | **専用テーブル** | — |

**「写真OK」を facts に入れてはいけない。**事実ではなく本人の同意。
(a)「無効化」の意味が変わる、(b) 検索で「近いもの」として曖昧に扱われうる、
(c) **同意が無い人の写真を使う事故が無音で起きうる**。

**`ngNotes` も同じ理屈。**facts は類似検索で「引っ張り出す」もの、NG は当該顧客に
触れた瞬間に**無条件で全件がコンテキストに入る**べきもの。
取りこぼしが許される情報と許されない情報を、同じ機構に載せない。

### 持たないと決めた列

| | なぜ |
|---|---|
| `last_contacted_at` | 書き込む経路は「注文を記録した」と「アプローチで連絡したを押した」の 2 つだけ。**実際の連絡は個人の連絡手段で行われるので 1 件も入らない。**それを「最終連絡」として出すと、昨日連絡した相手が半年前に見える。**間違っている日付は、無い日付より悪い。**「最近連絡していない人」はお渡しからの経過日数で見る（お渡しか納品のどちらかは必ず記録される） |
| `first_visit_date` / `acquisition_channel` / `referrer_id` | 3 つとも画面に出るだけで、集計にもトリガーにも出てこなかった。`referrer_id` にいたっては入力する画面すら無い。紹介は記録に「高橋様のご紹介」と書けば、確定検索の全文一致で引ける |

### 実装したときに決めたこと

器を作る段（`..._facts.sql`）で決めた 4 つ。どれも「間違えたとき何が壊れるか」で
選んでいる。

**ラベルは全員が足せる。分類を直せるのは管理者だけ。**
新しい語は「事実を 1 件記録する」という通常の経路で生まれるので、INSERT を
管理者に絞ると**記録そのものが止まる**。一方 `category_key` は 1 行直すと全顧客の
見え方が変わるので、`app_settings` と同じ「店舗共通のルール」として扱う。
顧客データの「管理者は閲覧のみ」はここには効かない。
`fact_aliases` は逆で、通常の記録経路では生まれない（人が「これも同じ意味だ」と
気づいたときだけ増える）ので、INSERT から管理者に絞ってある。

**重複防止はラベル単位ではなく原文単位。**
`(customer_id, label_id, body)` の部分一意索引で、止まるのは同じ文の二重登録だけ。
`nulls not distinct` を付けてある — 既定では NULL 同士を別物と見なすので、
付けないとラベルの無い走り書きだけ二重送信が素通りする。
ラベル単位にすると「ゴルフ好きらしい」と「月2でラウンドしてる」のどちらかが
入らなくなる。どちらもゴルフだが**別の事実**で、片方を捨てると情報が消える。
無効化した行は索引の対象外なので、消したあと同じ内容を入れ直すことはできる。

**追記のみはポリシーでは守れない。**
UPDATE ポリシーは行を選べても列を選べないので、「`body` を書き換えて過去の事実を
消す」が通ってしまう。しかも無音。`app.guard_fact_append_only()` を BEFORE UPDATE で
置き、`invalidated_at` 系以外が動いたら例外にしている。
ついでに `invalidated_by_staff_id` もここで本人に固定する（画面から渡させると嘘を書ける）。

**`search_chunks` はアプリから 1 行も書けない。**
書けるのは `worker_role` だけで、`authenticated` には権限ごと与えていない。
未処理のキューは別テーブルにせず、`customer_facts left join search_chunks` が
NULL の集合をそのまま使う — キューを持つと「入れ忘れた事実」という無音の失敗が
生まれるが、外部結合なら**事実が存在する限り必ず拾われる**。
`customer_facts` の列にしなかったのは、再埋め込みが追記のみのテーブル（と上の
トリガー）を触らずに済むのと、6KB のベクトルを人が実際に引く行に載せないため。

### `lib/ai/` の lint は 2 段階で入れる

いま入っているのは `supabase().from(` の禁止だけ。`lib/data/*` の import まで
禁じると `lib/ai/agent-tools.ts` が即座に落ちるが、あれは
`app.search_customers()` を入れる回に丸ごと書き換わる。**そのときに
`no-restricted-imports` を足す。**

## RAG は入れる。ただし網羅性の担保は SQL が持つ

「キーワード検索では無理、NotebookLM のような RAG に」という指摘は正しい。
ただし全部を RAG にすると主要要件が壊れる。

「ゴルフが趣味な人って誰だっけ」を top-k で返すと、該当12名のうち7名が
**静かに落ちる**。現れ方は「ゴルフ好きなのに案内が来なかった人が 7 名いる」で、
**誰も気づかない**。NotebookLM が top-k で許されるのは答えが「文書のどこかにある
1 つの事実」だからで、ここでの問いは「該当者の全員」なので性質が違う。

| 種類 | 例 | 機構 |
|---|---|---|
| 網羅性が要る | 「ゴルフが趣味な人」「最近連絡してない人」 | **確定検索（SQL）**。全件返す |
| 曖昧な想起 | 「アウトドア系が好きな人いたっけ」 | **RAG**。「近いもの」と明示する |
| その人を知る | 「時枝さんってどんな人だっけ」 | **検索不要**。facts 全件をそのまま入れる |

**顧客が特定できている問いに RAG は要らない。**

### RAG を入れるからこそ正規化が要る

- **チャンクの単位** — `"ゴルフ・ワイン・読書"` を 1 チャンクにすると
  「ワインが好きな人」でスコアが薄まる。1 事実 1 行がチャンク設計そのもの
- **メタデータフィルタ** — RAG で最も効くのは「ベクトル検索の前に絞る」。
  文字列 1 本だと `where` に書ける列が存在しない
- **出典** — NotebookLM が信用されるのは引用が出るから
- **ハイブリッド検索** — ベクトル単独では精度が出ない。
  **label という正規化キーが RAG のためにこそ必要**

### `app.search_customers()` — LLM にツールを選ばせない

ツールを 2 本に分けて「網羅が要るときは確定検索を使え」とプロンプトで指示する解は
**採らない**（RLS を採った理由と同じで、作法は必ず破れる）。
**1 本にして中で両方走らせる。**

- `match_type='exact'` は **LIMIT なしで全件**。「ゴルフが趣味の方は12名です」と言い切れる
- `match_type='similar'` は「近いもの」として別枠
- LLM は選択を間違えようがない

## 採寸を jsonb にしない理由

**公平に言うと、描画だけなら jsonb で足りる。**JOIN が要らず、型がそのまま乗り、
項目が増えても DDL を打たなくていい。

**「行をまたぐ問いが書きにくい」も決定打ではない。**どのみちビューに閉じ込めるので、
書きにくさはビューを書く 1 回に閉じる。

**決定打は型と制約。**jsonb だと `actual` に文字列が入っても通り、存在しないキーは
静かに NULL を返す。OCR が主動線になり手入力が退けられた（`5ef0d88`）ので、
人の目を通らない値に対する境界がここしか残らない。

ただし OCR 側にも既に 1 枚防御がある（`route.ts` の `FIELD_KEYS` enum）。
**DB の FK は 2 枚目**であり、当初の主張はその分弱い。2 枚目が効くのは
手入力・将来のインポート・エージェントに書き込みを許した場合。

規模は論点にならない（3,000 × 3 × 33 ≒ 30万行）。
「EAV より jsonb が単純」は 100万行以上の議論。

## PITR を入れない → 「消えない」ことを設計で担保する

Supabase PITR は +$100/月でインフラ費が 3 倍になる（$46 → $146）。採らない。

| 設計判断 | バックアップ観点での意味 |
|---|---|
| **顧客の物理削除を許さない** | 誤削除が原理的に起きない |
| **`customer_facts` は追記のみ**（訂正も新規行） | 過去の事実が消えない |
| **`change_log` に全書き込みが残る** | 「昨日の誤操作」を DB 内で辿れる |

PITR が本当に要るのはディスク障害と、誤ったマイグレーションを本番に流したとき。
後者は「マイグレーションを頻繁に打つ時期だけ一時的に有効化する」で足りる。

## アプローチ — `trigger_key` 設計をそのまま採る

当初 `approach_states` + `approach_resolutions` の 2 表分割を提案したが**取り下げた**。

**レコードが有る＝対応済み、無い＝未対応。**状態を持たないので上書き事故が起きず、
「半年をスキップしても 1 年後は出す」「今年の誕生日を見送っても来年は出す」が
自然に成立する。DB では `unique (trigger_key)` を張るだけ。

### 記念日の ID を位置由来にしてはいけない

モックは `anv-{customerId}-{i}`。`trigger_key` にこの id が埋まるので:

```
記念日 [誕生日(i=0), 結婚記念日(i=1)]
「誕生日」をスキップ → 'anniversary:anv-cust1-0:2027' が残る
あとで誕生日を消す → 結婚記念日が anv-cust1-0 に繰り上がる
→ 対応済みと判定され、結婚記念日のアプローチが永久に出ない
```

順序を入れ替えただけでも起きるうえ、完全に無音。**必ず uuid。**

### 店舗が変えられるのは「やってみないと分からない数字」だけ

| | 置き場所 | なぜ |
|---|---|---|
| お渡し後フォローの節目 | **`app_settings` の 1 行** | 声をかける間隔の適切な長さは、回してみないと分からない |
| 記念日の予告日数 | **`app_settings` の同じ行** | 同上。当初は「1 週間前は店舗として確定した決めごと」として `lib/constants/approach.ts` に固定していたが、声をかける準備に要る日数は店舗ごとに違った |

これで `app_settings` が戻った。いちど「店舗が変えられる数値が 1 つも残らない」と
判断して畳んだテーブルなので、**増やすときは毎回この基準に照らす**。設定が増えるほど
「この画面はこう出ているはず」という前提が人ごとにずれていく。

### 書き込みポリシーで `app.is_admin()` を呼ぶのは店舗共通ルールだけ

「管理者は閲覧のみ」は**顧客データ**の原則で、ここには効かない。
`app_settings` は 1 つの値が全スタッフの画面の出方を変えるので、
むしろ絞るほうが正しい（`revenue_targets` が他人の目標を管理者だけに開けているのと同じ）。

### 売上目標 — 「未設定」を行の有無で表すと、消せることが機能になる

目標は本人が立てるもので、他人のぶんを触れるのは管理者だけ。**閲覧だけは全員**
（週次ミーティングで並べて見る運用なので、他人の数字が見えないと成立しない）。

「未設定」は `amount = 0` の行ではなく**行が無いこと**で表す。0 の行にすると、
ダッシュボードと `goal-panel` が `target === null` で「未設定です」に分岐している
ところへ「目標 0 円」が流れ込み、達成率がゼロ除算になる。

**その結果、DELETE が塞がっていると目標の保存そのものが落ちる。**実際に落ちていた。
`revenue_targets` にも「消えない」原則を横に広げて `revoke delete` していたが、
あれは PITR を入れない代わりに**顧客の記録**が消えないことを担保するためのもので、
月次の目標額は記録ではなく設定に近い。`..._revenue_target_delete` で開けてある。

**3 つの書き込みポリシーは同じ条件に揃える。**
`staff_id = app.current_staff_id() or app.is_admin()`。片方だけ直すと、
画面側の出し分け（`canEdit`）と食い違い、押せるのに通らないボタンが生まれる。

### 節目を変えたときに何が起きるかを鍵の形で決める

`trigger_key` に埋めるのは節目の**月数**（`post_delivery:{orderId}:6m`）。
順番（1 つめ・2 つめ）にすると、6 を 9 に変えたときに鍵が変わらず、
すでに半年で連絡した相手が「対応済み」と判定されて**9 ヶ月の通知が無音で出ない**。
月数を鍵にすれば鍵ごと変わり、節目を変えたら出し直す挙動になる。
すでに連絡した相手にもう一度出ることはあるが、**出ないより出るほうが安全側**。

## 注文 — 金額は紙に合わせず、店が持っている 1 本に合わせる

`5ef0d88` で生地マスタと標準価格が廃止され、金額は紙の右上と同じ 4 欄
（売上金額・割増金額・消費税・合計金額）になった。**これは間違いだった。**

紙に合わせれば転記が楽になるはずだったが、その欄は実運用で**空欄のまま流れていた**。
残ったのは、0 が 3 つ並んだところに人が数字を入れる画面と、「紙の金額欄が空欄でした」と
毎回言う無意味な注記だけ。読み取りにも金額を読ませていたが、読めるものが無かった。

**紙の形を写すことと、店が持っている情報の形を写すことは別物。**店が持っているのは
税込の 1 本だけだったので、画面も 1 欄（売上金額（税込））にした。読み取りでも扱わない。
金額は取り込んだあと注文カードの Popover から入れる。

`subtotal_amount` / `surcharge_amount` / `tax_amount` の 3 列は**落とした**
（`..._order_amount_breakdown`）。一度も 0 以外にならず、残っていること自体が
「どれが正なのか」を読む人に毎回考えさせていた。割増を分けて持つかの審議は
**「分けない」で決着**している。

**列に CHECK も再計算トリガーも張らない。**工場側が計算した消費税は端数処理が
不明で計算値と 1 円ずれうる。「人が入れた額が正」という原則を DB で壊さない。

### 内訳は「税の内訳」ではなく「売上区分の内訳」

3 列を落としたのと同じ機会に、金額の内訳を**任意で**持てるようにした。

| 列 | 区分 |
|---|---|
| `amount_suit` | スーツ |
| `amount_coat` | コート |
| `amount_accessory` | 小物 |
| `amount_shirt` | シャツ |

**軸が違う。**紙の 4 欄は「税抜がいくらで税がいくらか」を分けていたが、
店が知りたかったのは**「何がいくら売れたか」**だった。同じ「内訳」でも、
前者は一度も埋まらず、後者は入れたいと言われた。

決めたこと:

- **すべて nullable。**「未入力」と「0 円」を区別できないと、内訳を付けていない
  注文が「4 区分すべて 0 円」に見える。落としたばかりの 3 列と同じ失敗になる
- **「その他」区分は作らない。**したがって **4 つの和が `total_amount` に
  届かないのは既定の状態**で、CHECK を張ってはいけない。画面でも差額の表示は
  注記のまま（赤くしない）。ただし**保存の手前で 1 度だけ確認を挟む** —
  打ち間違い（桁落ち・二重計上）も区分に無い売上も、画面ではまったく同じ
  「差がある」形で現れ、注記のままでは前者だけが黙って保存されていたため。
  **止めるための関門ではなく、見たことを確かめるためのもの。**
  合計欄が正である原則も、DB を縛らない判断も変えていない
- **既定では画面に出さない。**「内訳を入れる」を押した人にだけ欄が出る。
  4 欄を常に並べて 0 を 3 つ見せたのが元の失敗だったので、同じ形にしない
- **集計はまだ合計だけ。**ダッシュボードと売上目標は `total_amount` の合算のまま。
  区分別の集計は、内訳が実データとして溜まってから足す
- 採寸の `item_types`（ジャケット / パンツ / ベスト / シャツ / コート）とは
  **別の軸**。「スーツ」は上下一式の売上区分で、対応するアイテム種別の id は無い

## 注文 — 着装写真は入れてから撤回した

判断が 2 度折り返しているので、履歴だけ追うと往復に見える。順に:

1. **持たない**（初期）— 削除請求への対応を DB だけで完結させ、保持する
   個人情報を減らすため。`config.toml` の `[storage]` も無効にしていた
2. **持つ**（`..._order_photos`）— 紙のカルテには最初から写真が貼ってあり、
   アプリに無いぶんがスタッフの個人端末に溜まる（いちばん悪い状態）という理由。
   代わりに削除を 2 段にした（クライアントが Storage を消してから RPC）
3. **持たない**（`..._drop_order_photos`）— **店が使わないと決めた。**

**2 の理由は間違っていなかったが、前提が違った。**「紙に貼ってあったのだから
要るはずだ」は店に確かめた結論ではなく、こちらの推測だった。使わない機能のために
顧客の画像を抱え、削除経路を 2 段にしていたことになる。

撤回で戻ったもの:

- 削除は `public.delete_customer()` **1 本**で完結する（SQL から Storage には
  手が届かないので、画像を持った瞬間に削除は必ず 2 段になる）
- `lib/utils/image.ts`（縮小）と `lib/data/order-photos.ts`（署名 URL）が消えた

**`config.toml` の `[storage]` だけは有効のまま**にしてある。false にすると
`storage` スキーマごと作られず、適用済みの `..._order_photos` が流れなくなって
`db:reset` が落ちるため。当てた migration は書き換えられない。

## 注文 — 日付は受注日・納品日・お渡し日の 3 つ

もとは `due_date`（納期）と `delivered_at` の 2 つだったが、`due_date` が実際に
保持していたのは発注書の「納品日」欄（工場から店に届く日）で、顧客に約束した納期では
なかった。名前だけが実態とずれていたので `arrived_at` に改名した。

| 列 | 意味 |
|---|---|
| `ordered_at` | 受注日 |
| `arrived_at` | 納品日。工場から店に届いた日。発注書から読み取れる |
| `delivered_at` | お渡し日。店から顧客へ渡した日。**顧客の都合で決まるので紙には無い** |

**お渡し後フォローの起点は `coalesce(delivered_at, arrived_at)`**（`v_customers`）。
お渡し日は入力漏れが起きる前提の列で、空を理由にフォローが一生立たないほうが害が大きい。
「納品日から N 日経ってもお渡し日が空です」と促す通知は `docs/todo.md`。

画面では `delivered_at` 由来の表示を**すべて「お渡し」と呼ぶ**。「納品」は工場→店にしか
使わない。両方を「納品」と呼んでいたのが、そもそも `due_date` の取り違えを生んだ。
内部値（`OrderStatus` の `delivered`、`TriggerType` の `post_delivery`）は変えない —
後者は `approach_resolutions.trigger_key` に埋まっていて、変えると対応済みの通知が
全件立ち直す。

**生地は `orders` に持つ。**上流の実装は受け取りが注文単位（「生地は 1 注文で
1 種類。紙が原反NO を 1 つしか持たない」）なのに保存だけ明細ごとにコピーしており、
`OrderItem.fabricId` だった頃の名残になっている。

**`color_family`（色系統）は復活させない**（店舗判断）。
「紺のスーツをまだ持っていない人」は引けなくなる。引けるのは原反ＮＯ の完全一致まで。
